Mid-term Project Report: Distributed KV Store with Pluggable Cache Eviction
By Om Agrawal, Surya Sunkari, Ayuj Verma

Idea/Motivation:

Raft is a consensus protocol that allows a cluster of servers to maintain a replicated state machine, ensuring that all nodes agree on the same sequence of operations even in the presence of failures. While Raft provides strong consistency, every read operation requires accessing the committed state machine, and every write must go through log replication (appending to the leader’s log, replicating to a majority of followers, and applying the committed entry). This process, while correct, adds latency to GET and PUT operations, depending on the implementation of the state machine.

This project adds a pluggable cache layer to a Raft KV store. Each server in the cluster maintains its own local cache that sits in front of its state machine. On a read, the server checks the cache first and returns if it hits, which bypasses the whole state machine lookup entirely. On a write, committed entries update the cache according to two strategies: write-through or write-invalidate (more information in System Architecture).

Cache eviction is needed because a cache has finite size: when it is full and a new entry arrives, some existing entry must be removed to make room. The policy that decides which entry to remove is the eviction policy. In a single-server system, eviction policy is purely a performance question. In a Raft cluster, it becomes more interesting: because all writes flow through the leader and propagate to every follower, writes keep all server caches in sync. But reads do not - any server can serve a read directly from its local cache, meaning each server's cache evolves independently based on the reads it happens to receive. Two servers holding identical state machines can therefore end up with entirely different cache contents, and different eviction policies will interact with this divergence in different ways depending on how read traffic is distributed across the cluster.

Rather than hardcoding a single eviction strategy, the system supports multiple pluggable eviction policies: Random, FIFO, LRU, LFU, SLRU. This project also plans to implement SIEVE and MAT, two novel eviction policies. Each of these policies can be selected at start up through the config. These policies all use different data structures and heuristics to decide which entry to evict when a cache is full. This design lets us directly compare how different eviction strategies perform under various distributed load patterns. The end goal is to have a benchmark that evaluates all policies across various workloads to understand which eviction policies succeed (or fail) under certain access patterns in a distributed setting.


System Architecture:

The system runs as a set of separate processes communicating over gRPC. A front-end process accepts Get and Put requests from clients and forwards them to a server node. Each server node runs as its own process and maintains three things: its own copy of the Raft log, its own committed state machine (a key-value dictionary), and its own local cache. Nodes talk to each other using gRPC calls defined in a shared protobuf schema, which covers both client-facing operations (Get, Put) and internal Raft messaging (AppendEntries, RequestVote). The front-end also exposes operations for starting and stopping individual server processes, which is how tests simulate node failures and recoveries.

Within each server, the cache sits between the incoming RPC handler and the state machine. When a Get request arrives, the handler checks the cache first and returns immediately on a hit, bypassing the state machine lookup entirely. On a miss, it reads from the state machine, stores the result in the cache, and returns. Writes skip the cache at the RPC layer entirely. Instead, a write first travels through Raft log replication, and only once the entry is applied to the state machine does the cache get updated. That update follows one of two configured strategies: write-through (the new value is written into the cache) or write-invalidate (the stale entry is removed). Each server also exposes a GetCacheStats gRPC endpoint returning hits, misses, evictions, invalidations, current size, capacity, and hit rate for its local cache.

The cache is implemented behind an interface with four operations: get, put, invalidate, and clear. A factory function maps a policy name to the corresponding implementation, which is what allows the policy to be selected through the config file with no changes to the server code. The config also sets cache capacity and write strategy. Setting the policy to none or the capacity to zero disables the cache entirely, falling back to reading directly from the state machine on every request.


Implemented Cache Policies:

Random: When the cache is full and a new key needs to come in, pick any existing key at random and throw it out. No tracking of access patterns, every key has an equal chance of being evicted. Simple and cheap, but makes no bet on which data is worth keeping.
FIFO (First In, First Out): Keys are evicted in the order they arrived. The cache keeps a queue: the oldest key sits at the front, and when space is needed, that front key gets removed. A key accessed a million times after insertion gets no special treatment. If it was the first one in, it's the first one out.
LRU (Least Recently Used): Every time you read or write a key, it moves to the "most recently touched" end of an ordered list. When the cache is full, the key at the other end, the one untouched the longest, gets evicted. The bet: if you haven't needed something in a while, you probably won't need it soon.
LFU (Least Frequently Used): Each key carries a count of how many times it has been accessed. When something needs to be evicted, the key with the lowest count goes first. The bet: a key touched once is less likely to be needed again than one touched a hundred times. As a tiebreaker between keys with equal counts, the one touched least recently goes first.
SLRU (Segmented LRU): The cache is split into two zones: a small probation zone and a larger protected zone. Every new key enters probation. Access it again and it gets promoted to protected. Keys are only evicted from probation, or protected if probation is empty. The idea: a single access could be a fluke, but two accesses suggests the data is worth keeping, so earn your way into the safe zone.

Cache Policies to be implemented:

SIEVE: The cache keeps keys in a circular order with a moving hand. Each key has a visited bit. When evicting, advance the hand. If a key is visited, clear its bit and keep going. Evict the first key that is unvisited. The idea: recently used keys keep their visited bit and survive, while keys the hand passes without touching are evicted. This mimics LRU-like behavior (recent keys survive) with less bookkeeping than full LRU and good performance on many traces.
MAT (Machine learning At the Tail): When evicting, build a small set of candidates (e.g. 10 entries near the tail of the eviction queue). A small ML model scores each candidate using features like access count, time since last access, and time since insertion. The lowest-scoring candidate is evicted. The model is trained incrementally from observed access patterns. The idea: learning happens only at eviction time and only on the tail, so ML stays cheap while still picking a reasonable victim.

Initial Experiments:

We run two kinds of tests. 

First, cache_policy_tests.py checks that each eviction policy works correctly on its own. It instantiates each policy (random, fifo, lru, lfu, slru), performs put, get, invalidate, and eviction operations, and asserts that the policy returns the right values and updates its internal stats. It does not use Raft or the network. These unit tests confirm that the policies implement the expected behavior.

Second, cache_integration_test.py checks that the cache behaves correctly when wired into the Raft KV store. It starts a five‑node cluster, sends Get and Put requests through the frontend, and inspects cache stats via the GetCacheStats RPC. The test reads its cache configuration from config.ini: policy (LRU), capacity (3), and write_strategy (write_through). With this setup, all six integration tests pass. At the end of the run we report final stats: hits, misses, evictions, and hit rate. For the operations in cache_integration_test.py, the stats are:


Cache stats: hits=9, misses=6, evictions=9, hit_rate=60.00%

These numbers come from a fixed sequence of operations (puts, gets on the same keys, filling the cache, repeated gets), so the results are reproducible for the same config. Together, the unit and integration tests show that the cache layer works and that we can collect real stats from the live system. That gives us a base for a broader evaluation: varying workloads (e.g., uniform, skewed, sequential), eviction policies, and write strategies, and measuring how each configuration affects our metrics.


Current Progress:
The caching layer is implemented and tested. In cache.py there is an abstract policy interface and five concrete policies: Random, FIFO, LRU, LFU, and SLRU. Each policy handles get, put, invalidate, and eviction and exposes a stats object with hits, misses, evictions, invalidations, current size, capacity, and hit rate. The policy name and capacity are chosen by a factory function, so policies are pluggable.

Configuration is done through config.ini under [Cache], with fields for policy, capacity, and write_strategy (write_through or write_invalidate). At startup, the server reads these values and creates the cache if enabled.

The cache is integrated into the Raft server’s request path. On a Get, the server checks the cache first and, on a miss, reads from the state machine and fills the cache if the key exists. On a Put, when the log entry is applied, the server either updates the cache (write_through) or invalidates the entry (write_invalidate). Each server exposes a GetCacheStats gRPC endpoint that returns the cache stats.

Unit tests in cache_policy_tests.py run each policy in isolation and check get/put, eviction, invalidation, and stats for correctness. The cache integration test starts a five‑node Raft cluster, sends Get and Put requests via the frontend, queries GetCacheStats from the leader, and asserts that hits, misses, evictions, and hit rate behave correctly. Both test suites pass with the current config.

Future Progress:
Planned next steps are the following:

We will add SIEVE and MAT eviction policies, build a benchmarking harness across different workloads, and run failure-case analysis on each policy.

SIEVE uses a hand pointer and visited bits instead of full LRU ordering. MAT uses a small ML model to pick eviction victims from a candidate set at eviction time.

The benchmark harness should support several workloads: uniform, Zipfian, hot key, scan, temporal locality, and write heavy. The idea is to run a matrix of policies x workloads x capacities, collect metrics (e.g. hit rates and evictions), and compare the results.

Failure‑case analysis means finding workloads where each policy does poorly and trying at least one mitigation then rerunning the benchmarks to see if the hit rate improves.

Optionally, each server could use a different cache policy so that policies can be compared in the same cluster, though that approach would require per-server configuration and additional testing to confirm correctness.
