Project: Distributed KV Store with Pluggable Cache Eviction 
Authors: Om Agrawal, Surya Sunkari, Ayuj Verma 
 
Problem Statement:  
Distributed Key-Value (KV) stores often rely on caching to keep latency low and reduce backend 
load. However, eviction that looks good in a single node benchmark can fail in distributed 
settings due to node churn, replication, network delay, consistency issues, and more. Our goal is 
to build a distributed KV store with an integrated cache layer, and then compare a set of eviction 
policies under workloads that test these distributed system stressors. 
 
Background:  
In a distributed environment, a cache has to balance two things: miss ratio and throughput. We 
also want stable tail latency, predictable behavior during node loss, and to avoid issues during 
high traffic across nodes. To do this, we will look at several popular cache eviction policies, as 
well as a few recently developed eviction policies, that cover a broad range of use cases. Some 
policies are “simple but fast” (Randomized, FIFO), some focus on recency/frequency (LRU, 
LFU, SLRU), and some are newer designs intended to be more scalable or smarter about what to 
evict. For example, SIEVE is a recent eviction algorithm built to be simpler than LRU while still 
performing well on cache traces, and it is designed to reduce the amount of expensive 
bookkeeping on each request. MAT (Machine learning At the Tail) is another recent approach 
that tries to make learned eviction practical by applying ML only to a small candidate set near 
eviction time (instead of predicting for everything). 
 
Proposed Approach: 
1.​ Build a distributed KV store with a cache layer: We will implement a basic distributed 
KV store similar to Raft. Each node will have a local in memory cache, as well as 
traditional storage. The cache will sit on the path for GETs, and cache eviction will be 
done through a generalized policy. 
2.​ Make eviction policies pluggable: We want to implement the following eviction policies 
behind one interface so that swapping policies does not change the rest of the system: 
a.​ Randomized, FIFO, LRU, LFU, SLRU (Segmented LRU), MAT, SIEVE 
3.​ Evaluate under normal and distributed workloads: Measure hit rate, number of evictions, 
latency, and more. We will also look into node rebalancing, replication side effects, and 
any added delay due to the caches. 
4.​ Pinpoint failure cases: We also want to see where certain eviction policies fail. Once we 
find points of failure amongst the eviction policies, we will attempt a fix and retest. 
 
Expected outcomes: 
After this project, we will have a working distributed KV store with an integrated cache and a 
clean, pluggable eviction interface. We will also have a repeatable evaluation  system with 

distributed stress tests, which we will use to compare classic eviction policies with newer ones 
(SIEVE, MAT). Additionally, we will have at least one documented failure case and one 
attempted mitigation with experimental evidence.
